# ADR-0049 — PostgreSQL transport: terminate and re-originate, not substitute

**Status:** Proposed
**Date:** 2026-08-30
**Supersedes:** none
**Related:** ADR-0012 (per-uid narrow-trust CA), ADR-0023 (closed audit event set), ADR-0026 (TLS termination scoped to bound hosts), ADR-0035 (no credentials in operator URLs), ADR-0047 (explicit binding scope; the rate-ceiling rejection and the "not an API firewall" line)

## Context

Every credential kow brokers today is a string that appears verbatim inside an HTTP request. That is what makes the injector taxonomy work: `header`, `body`, `multi`, and the four token-minting and signing types all end in "write these bytes into the request before it goes upstream." The agent holds a placeholder, kow swaps it, G1 holds because the real bytes never entered the agent's address space.

The ask is to extend that to a PostgreSQL password. The framing in the ask — *"replacing a postgres password on the fly"* — is the thing this ADR has to correct first, because it does not survive contact with the protocol.

**Postgres does not put the password on the wire.** Since 10, the default and only serious authentication method is SCRAM-SHA-256 (RFC 5802 / RFC 7677), a challenge-response exchange in which the client proves knowledge of the password without transmitting it. The client derives `ClientKey` from the password, salt, and iteration count, then XORs it against an HMAC over a transcript that includes a server-chosen nonce. There is no field in that exchange containing the password, so there is no field to substitute. A byte-substituting proxy has nothing to substitute.

The two weaker methods do not rescue the idea either. `md5` hashes the password with the username and then again with a per-connection server salt, so a substituting proxy would need the real password anyway *and* would have to recompute the digest — at which point it is not substituting, it is authenticating. Only `password` (cleartext) auth is a literal byte swap, and requiring an operator to downgrade `pg_hba.conf` to cleartext in order to install a security tool is not a trade we get to offer.

The second structural problem is routing. The [StartupMessage](https://www.postgresql.org/docs/current/protocol-flow.html) carries user, database, protocol version, and optional run-time parameters. **It does not carry the target host.** There is no `Host:` header and no SNI to cross-check, so G3 — per-request destination consistency from CONNECT target + SNI + Host — has no inputs on this transport. And there is no `PGPROXY` environment variable: libpq clients take a host and port, so kow cannot be interposed by an env var the way `HTTPS_PROXY` interposes it today. Being pointed at is the only way in.

Prior art confirms both readings. [PgBouncer's SCRAM pass-through](https://www.pgbouncer.org/config.html) — the closest thing in the ecosystem to "proxy that does not hold the plaintext" — works by harvesting the *client's* SCRAM keys and replaying them upstream, and is documented as requiring that client authentication also use SCRAM, that the pooler's database entry not pin a username, and that the stored secrets be byte-identical on both sides ([issue #508](https://github.com/pgbouncer/pgbouncer/issues/508), [Crunchy Data](https://www.crunchydata.com/blog/pgbouncer-scram-authentication-postgresql)). That mechanism is unavailable to us by construction: it requires the client to know the password, and the entire premise here is that it must not.

What everyone who solves this actually does is terminate the client's connection and open their own. [AWS RDS Proxy](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy-secrets-arns.html) authenticates to the database with a Secrets Manager secret on the back leg while the app authenticates to the proxy on the front leg. [Teleport](https://goteleport.com/docs/enroll-resources/database-access/enrollment/self-hosted/postgres-self-hosted/) issues the client a short-lived x509 certificate and has its Database Service mint its own client cert or IAM token upstream. [StrongDM](https://docs.strongdm.com/admin/resources/datasources/postgresql) states the property directly — the proxy authenticates on the user's behalf and never surfaces a credential. And [Deno's Claw Patrol](https://deno.com/blog/clawpatrol), which is the most direct competitor to kow and is explicitly named in `docs/comparison.md`, describes exactly this for the non-HTTP protocols: *"completes the upstream authentication handshake with the real credential, then proxies the authenticated session back to the agent."*

So the question is not whether it is possible. It is possible, it is well-trodden, and a competitor already shipped it. The question is what it costs kow to do it, and that cost is the substance of this ADR.

## Decision

**Ship PostgreSQL as a second transport that terminates and re-originates, not as a tenth injector type.** kow speaks the server side of the protocol to the agent and the client side of the protocol to the database, performs the real SCRAM exchange upstream itself with a secret fetched just-in-time from the backend, and after `AuthenticationOk` becomes an opaque byte pump for the life of the session.

Concretely:

1. **The listener is the binding.** Because the wire carries no destination, routing cannot be parsed out of the connection — it must be structural. Each Postgres binding gets its own loopback listener port, declared in config, mapping one-to-one to one upstream `host:port` and one secret. `PGHOST=127.0.0.1 PGPORT=15432` reaches exactly one database and nothing else. This replaces G3 rather than weakening it: a destination that cannot be expressed cannot be mismatched. The rejected alternatives are recorded below.

2. **The agent presents a placeholder, and it is a real credential — for kow.** The libpq password environment variable carries an opaque kow-minted token, which keeps the operator's mental model and the `kow env` ergonomics uniform with the HTTP path. kow authenticates the client hop against that token using SCRAM-SHA-256 with a per-install salt, so it is a capability scoped to one listener and a bearer of nothing upstream. **A loopback port is reachable by every process on the host, at any uid**, so this token is the whole of the client-hop access control and is specified as such: ≥128 bits from the OS CSPRNG, minted at binding-creation time, stored only where the vault-side placeholder already lives, revoked by re-minting plus a restart, and compared in constant time. On a Unix-domain listener, `SO_PEERCRED`/`LOCAL_PEERCRED` uid checking is the stricter option that needs no client-side secret at all, mirroring the per-uid key derivation of ADR-0012, and is the recommended posture on a multi-uid host.

3. **kow owns TLS on both legs, and must default to verifying upstream.** Terminating the connection takes the ability to verify the server away from the client — the agent can no longer tell a real database from anything kow connected to. Upstream connections therefore default to `verify-full` semantics against the system trust store, and a binding may not downgrade below `verify-ca` without an explicit, audited opt-in. This is a *new obligation* the HTTP path never had, and getting it wrong silently downgrades every routed client's transport security. On the front leg kow answers `SSLRequest` with `S` and presents a cert from the same narrow-trust CA as ADR-0012, so `sslmode=verify-full` works for a client that points `PGSSLROOTCERT` at it; kow does *not* answer `N`, because a client that asked for TLS and silently got cleartext loopback is a downgrade kow should never author. **Channel binding is refused explicitly**: kow offers `SCRAM-SHA-256` and never `SCRAM-SHA-256-PLUS`, because a terminating proxy cannot honour a binding whose entire purpose is to detect it. A client configured with `channel_binding=require` therefore fails loudly at connect time rather than believing an end-to-end property it does not have.

4. **Splice after `AuthenticationOk`; parse nothing afterward.** kow forwards the server's own `ParameterStatus`, `BackendKeyData`, and `ReadyForQuery` verbatim, then copies bytes in both directions without interpreting them. Passing `BackendKeyData` through unchanged is what keeps `CancelRequest` working — it arrives on a *separate, unauthenticated connection* carrying only PID and secret key, and a proxy that rewrote the key would break Ctrl-C in `psql` in a way that looks like a hang, a documented failure mode in this class of tool. Port-per-binding makes the cancel path stateless as a side effect: a `CancelRequest` on listener *L* can only mean the one upstream *L* is bound to, so kow opens a connection there and forwards the packet verbatim, with no session map to grow, expire, or collide. It authenticates nothing, exactly as the protocol specifies, and the secret key it carries came from the real server.

5. **kow does not inspect SQL, and the scope lever is the database role.** This is the load-bearing decision and it is deliberately the unfashionable one. On the HTTP path, `methods:` and `paths:` are what bound a credential's blast radius once injected (ADR-0047). Their honest Postgres analogue is SQL verbs and table names, which is what Claw Patrol gates. kow will not: ADR-0047 already refused payload inspection on the grounds that it turns a credential proxy into an API firewall with a per-service rule set, and a SQL parser is that refusal's hardest case, not its exception — comments, dollar-quoting, `DO $$ … $$`, nested CTEs, and driver-side prepared statements all make verb matching an arms race against a language designed for expressiveness. **A Postgres binding is therefore unscoped by construction, and the narrowing lever is the credential itself: bind a `GRANT SELECT`-only role.** That is enforced by the database, cannot be evaded by lexical tricks, and is strictly stronger than anything kow could enforce in front of it. Because the product language says "credential isolation," an operator can bind a superuser and still believe kow scoped the access — so least privilege is a *stated requirement*, not a suggestion: the docs lead with the role, and `kow doctor` probes the bound role's attributes and warns loudly on `rolsuper`, `rolcreaterole`, or `rolbypassrls`.

6. **A denied or unbound connection gets `28P01`, and every denial class is indistinguishable.** G5's enforcement-by-omission — forward the placeholder and let the upstream's own auth failure surface — has no analogue here, because there is no destination to forward *to*; kow chose the upstream. The nearest-equivalent behaviour is to answer the client with the protocol's own authentication-failure `ErrorResponse` (`SQLSTATE 28P01`), which is what an ordinary wrong password produces and therefore reveals nothing about proxy mechanics. A bad placeholder, a listener with no live binding, a vault fetch failure, and an upstream credential that the database rejected must all produce the same bytes to the client and be separated only in the audit log; the deny path is padded to a fixed floor so timing does not reintroduce the oracle the error text avoids. G5's *intent* — never become a side channel that tells a probing agent which destinations are bound — is preserved; its mechanism is not portable.

7. **Sessions have a maximum age.** G8 degrading to connect-time-only is not merely staleness — a spliced session outlives the credential that opened it, so a pooled client can hold access indefinitely through a rotation, which defeats emergency revocation. Every Postgres binding therefore carries a `max_session_age` with a bounded default, after which kow closes the connection and the client reconnects and re-authenticates. Operators additionally get an explicit kill: `kow pg kill <binding>` drops live sessions on that listener, which is the control an incident actually needs.

8. **New audit event types, contract version bump.** `pg_session_opened`, `pg_session_closed`, `pg_auth_denied`, and `pg_upstream_auth_failed` go through the ADR-0023 closed-set process with declared field allowlists. The `inject_decision` fsync-before-upstream-write ordering of G6 applies to the point of upstream authentication rather than to each request, since after the splice there are no per-request decisions to record.

9. **Original implementation, no vendoring.** SCRAM-SHA-256 client and server are written from RFC 5802/7677 and the PostgreSQL protocol documentation. Both leading open-source references are unusable as code: Neon's proxy and PgBouncer are not Apache-2.0-compatible imports for us under hard constraint 9, and the same constraint has been met before for SigV4, HMAC, and JWT.

**Ships opt-in and marked experimental**, behind a new top-level `postgres:` config section rather than the `secrets:` map, because a listener with a lifetime and a session is not a request and does not belong in a taxonomy built for requests.

## What this costs, stated plainly

The honest summary is that this is not an extension of kow's architecture — it is a second architecture in the same repository.

The HTTP path is a mitmproxy addon in a request hook: stateless, one decision per request, ~2,500 statements of total program. The Postgres path is a long-lived TCP server with per-connection state, two independent TLS contexts, a hand-written SCRAM implementation on both sides of the exchange, and a session that lives for hours after the only decision has been made. It shares the backends, the audit log, and the config loader. It shares nothing else — not mitmproxy, not the injector interface, not `decide()`, not the request-scoped policy model.

Three of the nine invariants change meaning. G3 is replaced by structural routing rather than satisfied. G5 is replaced by a protocol-native equivalent. G8 — rotated secret picked up within TTL — degrades to *connect-time plus `max_session_age`*, because a spliced session outlives the credential that opened it; decision 7 bounds that window rather than closing it, and the bound is a session lifetime, not a TTL.

And the guarantee that arrives is narrower than the one on the HTTP path. The agent genuinely never holds the database password, which is the whole G1 claim and it holds cleanly. But an agent talking to an unscoped Postgres role through kow can `DROP TABLE` as easily as `SELECT 1`, and kow will not know. That gap is real, it is the gap a competitor closes with SQL parsing, and decision 5 says out loud that kow closes it with a `GRANT` instead.

## Rejected alternatives

**Byte-substituting the `PasswordMessage`.** The literal reading of the ask. Works only against `password` (cleartext) auth, fails structurally against `md5` and SCRAM, and would require operators to weaken `pg_hba.conf` to adopt a security tool. Rejected outright.

**PgBouncer-style SCRAM pass-through.** Elegant, and unavailable: it requires the client to derive its own client keys from the password, which is precisely what the threat model forbids.

**Encoding the target in `dbname` or the `options` run-time parameter** (e.g. `dbname=kow:prod-analytics`, or `options=-c kow.target=…`). Fewer listeners, and it lets one port serve many bindings. Rejected because it makes the destination a *parsed, agent-supplied field* — the agent picks its own upstream from a string it controls, which is a validation surface where the port-per-binding design has none, and it mangles the `dbname` the client thinks it connected to. A wrong parse here is a confused-deputy bug of the same shape ADR-0024 closed for GSM annotations.

**Doing nothing, and pointing at Postgres-native identity instead.** The strongest competing answer, and it deserves to be stated rather than strawmanned. On RDS or Cloud SQL, [IAM authentication](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy-secrets-arns.html) removes the password entirely. For self-hosted, [Vault's database secrets engine](https://developer.hashicorp.com/vault/docs/secrets/databases/postgresql) mints a short-lived role per session, and client certificates remove the password too. Any of these is a better answer than kow for an operator who already runs that infrastructure, and `docs/comparison.md` must say so. kow's remaining claim is specific and worth stating narrowly: those approaches all still put a *live, usable* credential inside the agent's address space, and a one-hour dynamic credential is many hours more than a `DROP TABLE` needs. Zero is a different property from short-lived. This ADR exists only for operators who want zero and do not have a Vault or an IAM to route through.

## Open before implementation

An adversarial design review of the first draft (cross-model, 2026-08-30) closed six items into the decisions above and left these as spec-level work that must land before any code. They are recorded here so acceptance is not mistaken for readiness.

- **Audit ordering, per path.** Decision 8 says G6 applies at upstream authentication, which is not specific enough. Client-auth denial, upstream-auth failure, and successful splice have different leak and observability properties, and each needs a named event with an explicit fsync-before-visible-effect point.
- **TLS specifics.** Hostname source for verification, SNI behaviour, IP-literal upstreams, custom trust roots, client-certificate auth to the database, and exactly which fields are audited on a downgrade opt-in.
- **The pre-auth state machine, enumerated.** `SSLRequest`, `GSSENCRequest`, `CancelRequest`, `NegotiateProtocolVersion`, and malformed or oversized startup packets each need a defined accepted-or-rejected response. "Splice after `AuthenticationOk`" describes the happy path only.
- **Bounds on every per-connection structure.** This project already treats an unbounded per-key map as a memory-exhaustion vector; a long-lived TCP server has more of them than a request hook does. Caps, expiry, and cleanup paths, named.
- **Config compatibility.** Bindings are `extra=forbid`. The new top-level section, listener-port allocation, and name collisions against `secrets:` need validation rules that reject ambiguity rather than resolving it.
- **A test oracle for the SCRAM implementation.** RFC test vectors, live interoperability against real PostgreSQL major versions, negative-authentication cases, nonce uniqueness, SASLprep, and constant-time comparison. Hand-written authentication crypto is the highest-risk code in this repository and does not get to be reviewed like ordinary Python.
- **Deployment ergonomics.** Listener addresses restricted to loopback by default, port-conflict handling, and generated environment output, so an operator cannot accidentally publish a database listener to a LAN.

## Consequences

**Good.** The G1 property extends to the credential class operators most often name as their scariest — production database access. Routing is structural rather than parsed, so the destination check gets stronger, not weaker, on the transport where it had the least to work with. Splicing after authentication keeps the steady-state path free of any protocol parsing, which caps both the CPU cost and the vulnerability surface. The design generalises: MySQL, Redis, and MongoDB are the same terminate-and-re-originate shape with a different handshake, so the transport abstraction is worth more than the one protocol.

**Bad.** A second concurrency model, a second TLS story, and a hand-written cryptographic handshake on both sides of an exchange — the highest-risk code this project has ever shipped, in a project whose entire value is being trustworthy. Three invariants change meaning and one (G8) genuinely degrades. Onboarding stops being an env var and becomes a listener the operator must point their client at. kow becomes responsible for upstream TLS verification the client used to do for itself. And the shipped guarantee is credential isolation without action scoping, which is a narrower promise than the HTTP path makes and must be documented as such or it will be misread.

**Out of scope.** SQL parsing, verb gating, table-level policy, connection pooling, query logging, and result-set inspection. Every one of them is a reason to use Claw Patrol or StrongDM instead, and `docs/comparison.md` should route people there without embarrassment.
